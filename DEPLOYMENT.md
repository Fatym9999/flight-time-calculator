# Обновление сайта через GitHub

## Что получится

| Действие владельца | Результат после включения автоматизации |
| --- | --- |
| Загрузить изменения в `dev` | Проверка и обновление `https://dev.moonhaze.ru` |
| Самостоятельно объединить `dev` с `main` | Проверка и обновление `https://moonhaze.ru` |
| Открыть pull request | Только проверки, без публикации |

Разработка всегда идёт в `dev`. Слияние выполняет только владелец. Публикации из `dev` и `main` включаются отдельно; по умолчанию обе выключены. Репозиторий `flight-test` для этой схемы не нужен, удалять его сейчас не требуется.

База Supabase общая, как согласовано с владельцем. Вход на поддомене выполняется отдельно. Изменения журнала после входа в один аккаунт видны на обоих сайтах. Записи без входа хранятся отдельно в браузере для каждого адреса. Возврат предыдущей версии сайта не возвращает прежние данные журнала.

## Файлы для загрузки в GitHub

Загрузить в **`dev`** репозитория `Fatym9999/flight-time-calculator`:

- `.github/workflows/deploy.yml`;
- `scripts/build-deploy-site.py`, `scripts/deploy-receiver.py`, `scripts/seed-deployment.py`;
- `tests/test_deploy.py`;
- `deploy/nginx-dev.conf.example`;
- `DEPLOYMENT.md`, `SERVER_DEPLOY_SETUP.md`.

Готовая папка `github-upload` содержит только эти файлы: существующие страницы калькулятора заменять при подключении автоматизации не нужно. На Mac скрытые папки показывает **⌘⇧.**. Если веб-загрузка пропускает `.github`, создать файл через **Add file → Create new file** с именем `.github/workflows/deploy.yml` и вставить его содержимое.

После загрузки откройте **Actions → Check and publish website**. Проверки должны пройти; публикация пока будет пропущена. При запрете Actions разрешить GitHub Actions и `actions/checkout` в настройках репозитория. Два варианта размещения исходников — с `cloud.html` и с готовым `index.html` — поддерживаются сборкой.

## Один раз настроить GitHub

Сначала друг выполняет [настройку сервера](SERVER_DEPLOY_SETUP.md). Пароли и закрытые ключи в чат и файлы репозитория не добавлять.

1. **Settings → Environments**: создать `dev` и `production`.
2. В каждом выбрать **Deployment branches and tags → Selected branches and tags**. Для `dev` разрешить только ветку `dev`, для `production` — только `main`. Не добавлять правила для тегов. Это ограничивает получение рабочего ключа тестовой веткой.
3. В **Environment secrets** каждого окружения добавить:

| Имя | Значение |
| --- | --- |
| `DEPLOY_PRIVATE_KEY` | Полный закрытый SSH-ключ соответствующего окружения, включая BEGIN/END |
| `DEPLOY_KNOWN_HOSTS` | Строка публичного ключа сервера, которую друг получил непосредственно на сервере |

Ключи `dev` и `production` разные. Это **environment secrets**, не общие repository secrets.

4. **Settings → Secrets and variables → Actions → Variables**: добавить repository variables:

| Имя | Значение |
| --- | --- |
| `DEPLOY_HOST` | `64.188.70.161` |
| `DEPLOY_PORT` | `22`, либо фактический SSH-порт |
| `DEPLOY_USER` | `flight-deploy` |
| `DEPLOY_ENABLED` | Сначала `false`; затем `true` для тестового сайта |
| `DEPLOY_PRODUCTION_ENABLED` | Оставить `false` до проверки основного сайта |

## Включение по шагам

1. Друг подготавливает тестовый сайт. Проверить `https://dev.moonhaze.ru/` и `/release.json` по HTTPS. Открыть калькулятор, проверить ввод, вход, синхронизацию и перезагрузку страницы.
2. Поставить `DEPLOY_ENABLED=true`, загрузить следующий коммит в `dev`. Проверить зелёный запуск Actions и обновление тестового адреса. Повторный запуск доступен через **Re-run all jobs**; он получает новый номер попытки.
3. Друг сохраняет старую папку основного сайта, создаёт начальный выпуск и меняет только `root` в действующем Nginx-блоке. Сертификаты и другие сайты остаются в существующей настройке. Проверить основной сайт и `/release.json`.
4. После успешной проверки поставить `DEPLOY_PRODUCTION_ENABLED=true`. Владелец сам объединяет pull request в `main`. С этого момента каждый такой merge обновляет основной сайт.

Кнопка **Run workflow** появляется, когда этот workflow есть в основной ветке. Для первого запуска на `dev` достаточно обычной загрузки файлов в эту ветку.

## Что проверяется и как вернуться назад

Actions проверяет синтаксис JavaScript, запускает тесты упаковки/установки и собирает оба варианта сайта. На сервер уходят только три HTML-страницы, семь JS-файлов, библиотека Supabase с лицензией и `release.json`. Секреты, SQL и инструкции не публикуются.

Новый выпуск сначала полностью загружается в отдельную папку. Сервер проверяет состав и контрольные суммы, затем переключает сайт одной операцией. Старые выпуски сохраняются. Actions проверяет по HTTPS идентификатор опубликованного выпуска; при неудаче пытается вернуть предыдущий выпуск. Это проверка доставки файлов, а не полноценная проверка входа и базы.

Команды ручного возврата и отключения публикаций приведены в инструкции сервера. Выпуски не удаляются автоматически; со временем друг сможет очистить старые, сохранив `current` и `previous`.

Используется стандартный Ubuntu runner без хранения артефактов и стороннего действия для SSH. Для публичного репозитория такие runner-запуски бесплатны. [Тарифы GitHub Actions](https://docs.github.com/en/billing/concepts/product-billing/github-actions), [окружения и ограничения веток](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments).
