# Настройка тестового входа

Ветка: `test/experiments`. Основной сайт и `main` не публиковать и не изменять без разрешения владельца.

## Что готово

8 октября 2026 владелец подтвердил реальную доставку письма Resend и показал экран успешного входа. После ошибки SMTP 535 владелец создал новый ключ Resend и сохранил его в Supabase. Старый ключ больше не считать действующим. Подготовлен отдельный облачный журнал: см. `SYNC_SETUP.md`; SQL и синхронизация на настоящей базе ещё не проверены.

Страница `registration.html` использует Supabase Auth: запрос кода, проверка, сохранение сессии, повторная отправка и выход только из текущей сессии. Проверка кода выполняется сервером. Демонстрационного входа нет. Без конфигурации форма отключена.

Калькулятор продолжает хранить налёт в `flight-time-entries-v2`. Авторизация не читает, не переносит и не удаляет эти записи. Сессия хранится отдельно, с ключом `flight-time-auth-test-<project-ref>-v1`. Вход пока не добавляет синхронизацию. Индикатор аккаунта не является проверкой доступа к будущей базе.

## Подключение Supabase

Создан отдельный проект **flight-time-test** (`bjkdfalvbvgjnhxspjxy`) в **Fatym's Org**, регион `eu-central-1`, тариф Free. URL и публичный ключ внесены в `auth-config.js`; CSP ограничена этим проектом. 8 октября 2026 включён `emailOtpEnabled: true` для проверки настоящего входа. Владелец подтвердил сохранение обоих шаблонов с кодом и настройку OTP: 6 цифр, 600 секунд. Доставка письма и успешный вход пока не проверены.

Проверено 7 октября 2026: `/auth/v1/settings` отвечает, Email включён, регистрация разрешена, автоматическое подтверждение почты выключено. Security Advisors не вернул замечаний. Реальная доставка писем и вход ещё не проверены. Настройки шаблонов требуют входа владельца в Dashboard; доступный MCP не предоставляет команды изменения Auth config.

С разрешения владельца SMTP заменён с Brevo на Resend: `smtp.resend.com`, порт `465`, пользователь `resend`, отправитель `onboarding@resend.dev`, имя «Калькулятор налёта», интервал 60 секунд. Ключ `flight-time-test-smtp` с правом отправки сохранён только на стороне Supabase. Тестовый отправитель ограничен почтой аккаунта Resend — `<почта владельца>`. Для отправки другим пользователям нужен подтверждённый собственный домен. Доставка через эту связку ещё требует проверки владельцем.

1. Подключить плагин Supabase к аккаунту владельца и выбрать отдельный тестовый проект. Не использовать рабочую базу. Если проект ещё не создан, создать его в аккаунте владельца, предварительно проверив условия тарифа.
2. Включить Email provider, регистрацию новых пользователей и подтверждение почты. Установить длину OTP **6 цифр**, срок **600 секунд** и интервал повторной отправки **60 секунд**. Серверные ограничения обязательны: таймер страницы нужен только для удобства.
3. В шаблонах **Magic Link** и **Confirm signup** использовать содержимое `email-templates/sign-in.html`, тему «Ваш код входа — Калькулятор налёта». Нужна переменная `{{ .Token }}`, а не ссылка. Проверить оба сценария: новую и существующую почту.
4. Настроить Custom SMTP и подтверждённого отправителя. С 3 июня 2026 года новые Free-проекты со встроенной почтой не могут изменять шаблоны, поэтому для нашего входа по коду требуется собственный SMTP даже на первом тесте. Ограниченный тест встроенной почты со стандартными ссылками не проверяет этот сценарий. Пароль SMTP вводить только в настройках сервиса; не сохранять в HTML, Git или чате.
5. В `auth-config.js` заполнить `url` (`https://<project-ref>.supabase.co`) и `publishableKey` (`sb_publishable_...`). Это публичные параметры браузера. Секретные ключи и `service_role` здесь запрещены. После выбора проекта сузить `connect-src` в CSP страницы до его точного адреса.
6. Настроить Site URL на отдельный адрес тестового сайта. Вход реализован кодом, обработка ссылок и токенов из URL отключена. Для первого теста можно использовать локальный HTTP; для удалённого доступа нужен HTTPS. Не переключать публикацию основного GitHub Pages на эту ветку.
7. После проверки настроек SMTP и шаблонов установить `emailOtpEnabled: true`. Провести проверку доставки и входа на почте владельца; при неудаче вернуть `false` до устранения причины. Не считать готовность проекта подтверждением работоспособности почты.

## Локальная проверка

Из каталога репозитория:

```sh
python3 -m http.server 8080 --bind 127.0.0.1
```

Открыть `http://127.0.0.1:8080/registration.html`. Для настоящего входа режим `file://` отключён. Локальный сервер доступен только на компьютере. Не помещать секретные файлы в обслуживаемый каталог.

```sh
node --test tests/auth.test.cjs
```

Тесты используют подменённые ответы Auth и DOM, не отправляют письма. Они не заменяют проверку реального проекта.

Перед завершением настройки проверить: доставку письма владельцу, неверный/просроченный код, успешный вход, обновление страницы, повторный вход и выход. Для тестов налёта использовать вымышленные записи на отдельном адресе. Проверить, что экспорт и существующие записи сохраняются после входа/выхода. Пока внешний проект не подключён, настоящая доставка писем не подтверждена.
