# Размещение калькулятора на Ubuntu и Nginx

Первая копия будет доступна по адресу **https://moonhaze.ru/flight-test/**. Сначала проверяем её; размещение на главной странице — отдельный следующий шаг. Работающий сайт на GitHub остаётся доступен.

## 1. Проверить домен и HTTPS

Публичный IP нового сервера, сообщённый владельцем: **64.188.70.161**. Проверка DNS 9 октября показала:

| Запись | Сейчас в публичном DNS | Требуемое действие |
| --- | --- | --- |
| A для `moonhaze.ru` | `31.31.196.17` | Заменить адресом `64.188.70.161` |
| AAAA для `moonhaze.ru` | `2a00:f940:2:2:1:1:0:256` | Заменить IPv6 нового сервера; если его нет, удалить старую AAAA только для этого имени |
| NS | `ns1.hosting.reg.ru`, `ns2.hosting.reg.ru` | Сейчас активна DNS-зона хостинга; редактировать записи там |

Обычная запись основного домена в панели обозначается `@` или пустым поддоменом. Удаление старой AAAA нужно, чтобы устройства с IPv6 не продолжали открывать прежний сервер. Изменение A/AAAA основного домена переводит его сайт на новый сервер; выполнять после настройки Nginx и загрузки файлов. DNS-серверы и почтовые записи при этом не менять.

При HTTPS-проверке с принудительным подключением к указанному IP и именем `moonhaze.ru` получен сертификат с `CN=*.hosting.reg.ru`, который не подходит этому домену. На сервере проверить правильный блок `server_name moonhaze.ru`, пути `ssl_certificate` и `ssl_certificate_key`, а также сам публичный IP в панели сервера. Не присылать приватный ключ.

Проверка из терминала после исправления Nginx, ещё до изменения DNS:

```bash
curl --head --max-time 15 --resolve moonhaze.ru:443:64.188.70.161 https://moonhaze.ru/flight-test/
```

Команда обращается к указанному серверу с правильным именем домена и проверяет сертификат. Не добавлять `-k`. После переключения DNS повторить без `--resolve`:

```bash
curl --head --max-time 15 https://moonhaze.ru/flight-test/
```

На момент проверки 9 октября 2026 года публичный `https://moonhaze.ru/` отдавал сертификат, который не соответствует имени `moonhaze.ru`. Сообщение проверки: `SSL: no alternative certificate subject name matches target host name 'moonhaze.ru'`.

Нужно сравнить публичный IP нового сервера с DNS-записями домена, включая A и AAAA, если она есть. На новом сервере проверить, что HTTPS-блок Nginx содержит `server_name moonhaze.ru` и использует сертификат именно для этого имени. Полученный сертификат сам по себе ещё не подтверждает правильную настройку Nginx. Не отключать проверку сертификата в браузере.

DNS-записи для сайта и записи для отправки писем через Resend решают разные задачи. TXT и CNAME почтового поддомена `login.moonhaze.ru` сохраняем.

## 2. Загрузить файлы

Используем уже отправленную папку **flight-time-main-publish**. Никакая сборка и установка Node.js для этой версии не нужны.

Создать папку на сервере:

```bash
sudo mkdir -p /var/www/flight-test
```

Через SFTP загрузить **содержимое** папки публикации туда. Итоговая структура:

```text
/var/www/flight-test/index.html
/var/www/flight-test/registration.html
/var/www/flight-test/local.html
/var/www/flight-test/*.js
/var/www/flight-test/vendor/supabase-2.117.3.js
/var/www/flight-test/vendor/supabase-LICENSE
```

Не создавать лишний уровень `flight-test/flight-time-main-publish/`. Файл `.DS_Store` пропустить. Для чтения статических файлов Nginx:

```bash
sudo chmod -R a+rX /var/www/flight-test
```

## 3. Добавить адрес в Nginx

Посмотреть действующую конфигурацию:

```bash
sudo nginx -T
```

Друг проверил: в выводе `nginx -T` нет `moonhaze.ru`. Поэтому нужен **новый файл сайта**, а не только фрагмент `location`.

Использовать `nginx-flight-test-site.conf.example`. В нём заменить оба пути `REPLACE_WITH_...` на действительные пути к сертификату домена и его приватному ключу. Если сертификат получен через Certbot, пути покажет:

```bash
sudo certbot certificates
```

Нужны строки `Certificate Path` и `Private Key Path` для `moonhaze.ru`. Если Certbot не установлен, найти пути в настройках того инструмента, которым получен сертификат. Содержимое приватного ключа никому не отправлять.

В выводе `nginx -T` проверить, какой каталог подключается директивой `include`. Если есть `include /etc/nginx/conf.d/*.conf;`, сохранить готовый файл как `/etc/nginx/conf.d/flight-time-test.conf`. Если используется только `include /etc/nginx/sites-enabled/*;`, сохранить в `/etc/nginx/sites-available/flight-time-test`, затем подключить:

```bash
sudo ln -s /etc/nginx/sites-available/flight-time-test /etc/nginx/sites-enabled/flight-time-test
```

Выбрать **один** способ подключения. Если файл или ссылка уже существуют, сначала проверить их; не перезаписывать чужие настройки. Главный `nginx.conf` и существующие сайты сохраняются. Шаблон нельзя применять с незаменёнными путями сертификата.

Новый файл направляет HTTP на HTTPS и открывает калькулятор только в `/flight-test/`. Корень `/` пока возвращает 404 — это ожидаемо для первой проверки.

Если позднее отдельный HTTPS-блок `moonhaze.ru` уже будет создан, можно добавить в него только `nginx-flight-test-location.conf` вместо создания второго блока.

Параметр `root /var/www` вместе с адресом `/flight-test/` направляет запросы в `/var/www/flight-test/`. Существующие сертификаты и остальные адреса сайта сохраняются. [Документация Nginx](https://nginx.org/en/docs/http/ngx_http_core_module.html#root).

Проверить конфигурацию:

```bash
sudo nginx -t
```

**Только если проверка успешна**, применить её:

```bash
sudo systemctl reload nginx
```

При ошибке исправить указанный файл; не выполнять перезагрузку с ошибочной конфигурацией.

## 4. Проверить работу

Открыть `https://moonhaze.ru/flight-test/` без предупреждения о сертификате. Проверить ввод налёта без аккаунта и сохранение после обновления страницы. Затем войти по почте, проверить свой журнал, экспорт JSON и вход с другого устройства.

Это копия интерфейса с подключением к **той же базе Supabase**: записи аккаунта общие с текущим сайтом. Не удалять записи ради теста. Вход в браузере на новом домене потребуется заново. Записи без аккаунта с GitHub автоматически не переносятся: для них есть экспорт и импорт JSON. Папки `/flight-test/` и `/` одного домена используют общее хранилище браузера.

Сейчас используется ввод кода из письма, без перехода по ссылке. Для этого переезда менять адрес Supabase в коде и настройки перенаправлений не требуется. Вход через Telegram подключим отдельным этапом.
