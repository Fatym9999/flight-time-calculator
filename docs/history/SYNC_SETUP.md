# Тестовая синхронизация

Код подготовлен в `test/experiments`; основной сайт не изменён. Владелец выполнил настройку и проверку SQL, подтвердил синхронизацию в двух вкладках и опубликовал отдельный тестовый сайт.

## Единая страница калькулятора

Без входа `cloud.html` сразу позволяет добавлять задания и сохраняет их в отдельном ключе `flight-time-test-guest-v1`. Ключ основного сайта `flight-time-entries-v2` не читается и не меняется. При входе страница показывает облачный журнал, при выходе возвращает локальные записи без аккаунта. Автоматического объединения списков нет; перенос выполняется через экспорт и импорт. Форма позволяет печатать во время загрузки аккаунта, но облачное сохранение доступно только после чтения свежего журнала. Ошибка доступа к локальному хранилищу отображается явно.

Публикация подготавливается командой `python3 scripts/build-test-site.py` в соседнюю папку `flight-time-test-publish`. Главная `index.html` — единый калькулятор, обе ссылки со страницы регистрации ведут на него. `local.html` сохранён для старых прямых ссылок, без дополнительной кнопки журнала. Переходов на второй калькулятор в новой главной странице нет.

## Подключение

1. В Supabase выбрать **flight-time-test**, открыть **SQL Editor → New query**.
2. Вставить весь `sql/sync-setup.sql`, нажать **Run**. Выполнить один раз: повторный запуск остановится на уже существующей таблице, не удаляя её.
3. В новой вкладке SQL Editor выполнить `sql/sync-verify.sql`. Ожидаемый результат: `OK: revision checks, idempotency, validation and account isolation passed; test data rolled back`. Проверка создаёт временные тестовые аккаунты и записи внутри транзакции, затем отменяет их. При ошибке сообщить её текст; не импортировать личные данные.
4. Открыть `http://127.0.0.1:8080/cloud.html` в том же браузере, где выполнен вход. Добавить вымышленное задание на 1 час 15 минут, затем обновить страницу: запись должна сохраниться.
5. Открыть вторую вкладку журнала: проверить появление записи, добавление и удаление. Открытая страница обновляется раз в 30 секунд, при возвращении на неё и кнопкой «Обновить журнал».
6. Проверить конфликт: отключить обновление/интернет в одной вкладке, изменить журнал в другой. Старое сохранение должно блокироваться с просьбой обновить журнал. Поля ввода при ошибке остаются на странице.

## Данные и доступ

`index.html` остаётся обычным локальным калькулятором. Новый `cloud.html` не читает и не меняет `flight-time-entries-v2`. В аккаунте изначально пустой журнал. Копия v2 совместима с облачным импортом: перенос производится только явным действием пользователя после тестов.

Каждому аккаунту принадлежит отдельная строка `flight_journals`. RLS ограничивает чтение, вставку и обновление владельцем. SQL-функция работает с правами пользователя (`security invoker`), проверяет владельца и предыдущую версию журнала. Повтор одного запроса не создаёт копий. Импорт и замена списка выполняются атомарно.

Это первый этап: требуется интернет. При сбое сохранение не объявляется успешным, дальнейшие изменения блокируются до чтения свежего журнала. Черновик остаётся только на открытой странице: не закрывать её до проверки сохранения. Локального офлайн-кэша облачных записей пока нет. Экспорт доступен для загруженного списка; резервные копии хранить отдельно.

## Проверка кода

```sh
node --test tests/auth.test.cjs tests/cloud.test.cjs
```

Тесты кода используют подменённый сервер; `sql/sync-verify.sql` проверяет настоящие SQL-права и версии после установки. На телефоне `127.0.0.1` указывает на сам телефон: для проверки двух устройств нужен отдельный тестовый HTTPS-сайт, который будем публиковать отдельно от основного.

Лимиты первой версии: 10 000 заданий, каждое числовое поле до 1 млрд, название до 40 символов. Список хранится целиком, что удобно для небольшого личного журнала; при росте объёма потребуется хранить полёты отдельными строками.

Документация: [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [RPC](https://supabase.com/docs/reference/javascript/rpc).
